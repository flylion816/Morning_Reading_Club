# 小程序功能升级方案：做更有调性的晨读营

- 状态：**大部分已实现、未提交、待验收**（2026-11-11，详见文末「十一、实施记录」）
- 姊妹篇：`docs/design/miniprogram-warmth-upgrade-2026-11-10.md`（UI「晨光」温暖升级方案）
- 范围：面向书友的新功能建议，按投入从小到大分三个梯队；每项写明怎么用、复用什么、要新增什么

## 一、结论

现在的系统功能已经很全：报名、支付、晨读、打卡、评论点赞、小凡看见、在场、活动、播客、结营视频、实录报告都有。**缺的不是功能数量，而是「只有这个晨读营才有」的东西。**

我的建议是沿着产品自己已经在用的词去长功能——凡人、共读、看见、在场、印记、明理实修——而不是去学打卡类产品的积分、等级和勋章。具体三步：

1. **先把已有的点亮。** 后端已经在记心情、连续天数、阅读时长、省份，但前端没用起来。日签、心情天气、同行感这三项投入小、见效快。
2. **再做一两个招牌功能。** 首推「慢递邮局」（开营写信、结营送达）和「我的 23 天」（结营纪念册），它们正好把 23 天的头和尾接起来。
3. **最后做更深的连接。** 看见卡、小凡周信、实修清单、读伴、声音打卡，按营里的反馈再定。

## 二、需要你确认的 6 件事

| # | 要定的事 | 我的建议 |
| --- | --- | --- |
| 1 | 总体取向：走「仪式感」而不是「游戏化」，不做积分、等级、勋章 | 认同这条线，后面所有功能都按它取舍 |
| 2 | 第一梯队做哪几项 | 日签、心情天气、同行感三项都做，体量都不大 |
| 3 | 招牌功能先做哪个 | 先「慢递邮局」，再「我的 23 天」；摘抄本排第三 |
| 4 | 下一期哪天开营 | 需要你告诉我。开营信必须赶在开营前上线，纪念册必须赶在结营前上线，排期由这两个日期倒推 |
| 5 | 心情天气谁能看到 | 个人的只有自己能看，营里只显示匿名汇总（如「今天 12 晴 5 多云 3 小雨」） |
| 6 | 小凡相关的 AI 内容怎么产出 | 继续现在的做法：线下批量生成、通过外部接口写入、小程序只负责呈现；不在小程序里做实时 AI 对话 |

## 三、调性罗盘：什么算「有调性」

从产品现有的语言里提炼四条取舍标准，每个功能都拿它过一遍：

1. **仪式感，不是游戏化。** 标记时间的流动（清晨、第几天、结营），而不是奖励刷任务。
2. **看见，不是评比。** 被小凡看见、被书友看见，而不是排名次。
3. **留得下来。** 做完能沉淀成一页日签、一封信、一本摘抄、一册纪念，而不是刷过就没了。
4. **慢一点。** 信要等 23 天才到，提醒一天最多一次，不催、不吵。

## 四、现有家底：已经有、但没用起来的

这些是做下面功能的地基，多数不需要新建数据：

| 已有的东西 | 现状 | 可以用来做 |
| --- | --- | --- |
| 打卡心情 `Checkin.mood`（happy / calm / thoughtful / inspired / other） | 前端写死成 `happy`（`miniprogram/pages/checkin/checkin.js:1148`），所以历史数据全是「开心」 | 心情天气 |
| 连续天数 `User.currentStreak` / `maxStreak` | 后端在算、接口在返回，小程序没展示；口径有问题（见方案一 G 节） | 手账、日签、纪念册 |
| 阅读完成记录 `UserReadingCompletion`（含每课阅读时长） | 只用于判断「已晨读」 | 同行感、累计晨读时长、纪念册 |
| 报名省份 `Enrollment.province` | 只在后台统计里用 | 「来自 14 个省市的书友」 |
| 小凡看见的周、月类型（`Insight.type` 含 weekly / monthly） | 没有对应内容和入口 | 小凡周信 |
| 外部写入接口 `/insights/external/create` | 用于导入小凡看见 | 周信、结营信的批量写入 |
| 海报与长图能力（沉浸阅读「分享此刻」、打卡长图模板库） | 已稳定 | 日签、金句卡、纪念册长图 |
| 定时任务（`node-cron`，学习提醒、活动提醒、期次状态） | 已稳定 | 慢递信的定时送达 |
| 首页板块配置（后台可调顺序和显隐） | 已稳定 | 新板块按租户开关 |
| 积分与等级 `User.totalPoints` / `level`（每次打卡 +10） | 在记，前端没用 | **建议不要用**，见第八节 |

## 五、功能清单

规模说明：S = 几天内能做完、基本不动后端；M = 需要新接口或新数据表；L = 跨端、有运营或合规前置。

### 第一梯队：点亮已有

#### 1. 晨读日签

**一句话**：每天读完或打完卡，得到一张当天的日签——日期、节气、第几天、今日一句、自己写的一句话。

- **怎么用**：打卡成功的晨光仪式上多一个「生成今日日签」；选一个版式（晨光 / 纸墨 / 留白）；保存到相册或发给好友。当天完成后，首页今日卡片上也能再进。
- **今日一句从哪来**：默认取你在沉浸阅读里停留的那一段（「分享此刻」已经能定位当前段落），也可以换成课程的「摘一摘」。
- **为什么有调性**：把「打卡」从完成任务变成留下一页。它也是最自然的转发物，朋友圈里一张好看的日签比任何邀请文案都管用。
- **复用**：沉浸阅读的海报生成（`miniprogram/pages/reading-mode/reading-mode.js:917`）、打卡长图模板库、分享封面工具。
- **新增**：三个海报版式、一份节气表、各租户的小程序码图片。
- **规模**：S–M，不动后端。

#### 2. 心情天气

**一句话**：打卡时选一个「今天的心情天气」，23 天后得到一条属于自己的天气带。

- **怎么用**：打卡页在「可见范围」上方加一排天气：晴（明亮）、多云（平静）、微风（若有所思）、朝霞（被点亮）、小雨（有点沉）、雾（说不清）。点一下即可，可以不选。
- **在哪出现**：自己的打卡日记卡片；「我的」手账日历；每课的打卡区顶部显示匿名汇总「今天营里：12 晴 · 5 多云 · 3 小雨」；结营纪念册里的天气带。
- **为什么有调性**：晨读营讲「观心」。允许「小雨」和「雾」存在，比一律「开心」更诚实；看到别人今天也下小雨，本身就是一种陪伴。
- **复用**：`Checkin.mood` 字段和提交链路已经通了，只差界面。
- **新增**：枚举加一个「有点沉」；汇总接口；天气图标。历史数据全是写死的 `happy`，上线日之前的记录统一按「未记录」处理。
- **规模**：S。

#### 3. 同行感

**一句话**：让人感觉到「不是我一个人在读」，但不打扰任何人。

- **此刻同读**：清晨 5:30–8:00，首页问候区显示「此刻有 8 位书友也在读」；其余时间显示「今天已有 23 位书友读完」。
- **第几位**：读完和打卡成功时显示「你是今天第 9 位」。
- **来自哪里**：期次页显示「本期 86 位书友，来自 14 个省市」。
- **为什么有调性**：「共读」的感觉现在只能靠微信群和腾讯会议传递，小程序里是一个人在用。几个安静的数字就能把这层感觉补上，不需要聊天功能。
- **复用**：`UserReadingCompletion`、课节打卡人数、`Enrollment.province`、现有 Redis 缓存。
- **新增**：一个轻量的「开始阅读」上报和两个带缓存的计数接口。只显示人数，不显示名单；人数太少（如少于 3）时不显示。
- **规模**：S–M。

### 第二梯队：招牌功能

#### 4. 慢递邮局

**一句话**：开营第一天给结营那天的自己写一封信，封存 23 天，结营日清晨送达。

- **怎么用**：
  1. 开营第一周，首页出现「慢递邮局开张了」。点进去写信，提示语是「23 天后，你希望自己有什么不一样？」
  2. 选一枚邮戳，投递。之后只能看到信封和「信在路上，还有 22 天」，不能打开。
  3. 结营日早上 6 点送达，收到通知「有一封 23 天前的信到了」。拆信，信的旁边是你这 23 天的数字。
  4. 读完可以回一句话，和原信存在一起。
- **以后可以加**：给书友的慢信（次日清晨才到）；给下一期陌生书友留一句话（下一期开营第一天随机送到）。第一版只做写给自己的，内容完全私密，风险最低。
- **为什么有调性**：整个产品最「慢」的一个功能，正好对抗打卡类产品的即时刺激。它给 23 天加了一个头和一个尾。名字借自你们做过的《同理小镇的慢递邮局》。
- **复用**：定时任务、站内通知、方案一里「小凡的信」的信纸样式。
- **新增**：信件数据表（含送达时间、拆信时间、回信）、写信页和拆信页（放分包）、一个定时送达任务、一个订阅消息模板（每个租户都要申请）。
- **规模**：M。
- **排期提示**：写信和封存必须在开营前上线；送达和拆信可以晚 20 天再上，时间上很从容。

#### 5. 我的 23 天（结营纪念册）

**一句话**：结营那天，每个人收到一份自己的 23 天，一页一页往下翻。

- **内容**（没有数据的页自动跳过）：
  1. 封面：期次名、你的名字、一枚印章
  2. 你读了多少天、写了多少字、晨读一共多少分钟
  3. 最早的一次打卡是几点
  4. 你的心情天气带
  5. 被点赞最多的那篇打卡（摘录）
  6. 你摘下的句子
  7. 这一期最常来看你的三位书友
  8. 小凡看见里的一段话
  9. 你的开营信和回信
  10. 封底：结营视频、实录报告的入口，以及「邀请一位朋友加入下一期」
- **为什么有调性**：结营现在有视频和 PDF 报告，但都是营方做给大家的；这一份是每个人自己的。它是整期情绪最高的时刻，也是下一期最好的招生素材（邀请页已经有了）。
- **复用**：打卡、评论、点赞、阅读完成、小凡看见的现有数据；长图生成；邀请流程；「我的」里的共读足迹印章。
- **新增**：一个汇总接口（期次结束时算一次并缓存）、一个纪念册页（分包）、一张分享长图。
- **规模**：M–L。
- **前置**：累计和连续天数的口径校准（见方案一 G 节）。

#### 6. 摘抄本

**一句话**：沉浸阅读时长按一段话「摘下来」，攒成自己的摘抄本；还能看到「12 位书友也摘了这句」。

- **怎么用**：长按段落 → 摘下来 / 写一句感想 / 做成金句卡。「我的」里多一个摘抄本，按期次归档，可以导出长图。被 3 人以上摘过的句子，在阅读页有一条淡淡的下划线和人数。
- **为什么有调性**：读书人的老习惯。「也摘了这句」是最安静的一种共鸣。
- **复用**：沉浸阅读已经按段落管理内容；小凡看见详情里按阅读位置发弹幕的做法可以参考。
- **新增**：摘抄数据表、摘抄本页、阅读页的长按菜单和热度下划线。
- **注意**：课程内容被后台改过之后段落序号会变，摘抄要存原文和文本指纹，不能只存序号。金句卡上标明书名和作者。
- **规模**：M。

### 第三梯队：更深的连接

#### 7. 看见卡

**一句话**：比点赞重一点、比评论轻一点——对一篇打卡说一句「我看见…」。

- **怎么用**：打卡下方多一个「看见」按钮，选一句开头：「我看见你的坚持」「这句话说到我心里了」「谢谢你愿意说出来」「我也是这样」，可再补一句（40 字内）。对方收到通知，并收进手账的「被看见」里。
- **为什么有调性**：「看见」是这个产品的核心动词，现在只有小凡在用。把它交到书友手里，也降低了「不知道评论什么」的门槛。
- **实现**：可以做成评论的一种类型，复用评论和通知链路。
- **规模**：S–M。

#### 8. 小凡周信

**一句话**：每周日晚上，小凡给每个人写一封这一周的小结。

- **怎么用**：周日晚首页出现「小凡给你留了一封信」，点开是信纸样式。
- **实现**：数据模型和写入接口都已具备（见第四节）。小程序侧主要是入口和信纸样式（方案一 I 节已包含）；内容仍由你线下的生成流程批量产出。
- **规模**：小程序侧 S；主要工作量在线下的内容生产。

#### 9. 实修清单

**一句话**：「明理实修」里的实修——每周给自己定一个小到不会失败的行动，每天点一下「今天做到了吗」。

- **怎么用**：每周一从三个建议里选一个（取自当周课程的「记一记」，也可以自己写），如「本周：先听完再开口」。之后每天首页一个小卡片：做到了 / 今天没有，可补一句话。周日自动带进打卡。
- **为什么有调性**：把读书和生活接起来。「今天没有」是一个被允许的答案，不扣分、不断连。
- **新增**：实修数据表、首页一个可开关的板块、后台配置每周建议。
- **规模**：M。

#### 10. 读伴

**一句话**：愿意的人可以配一位同期读伴，互相看得到对方今天读了没。

- **怎么用**：开营时自愿加入，系统随机配对。首页一行小字「你的读伴小林今天已读完」，可以「轻拍一下」（每天一次）。结营时互写一封慢信。
- **风险**：一方中途不读了，另一方会失落，需要「换读伴」和「读伴请假」；互动只开放轻拍、看见卡和慢信，不做自由聊天。
- **规模**：M–L，建议看前面功能的反馈再做。

#### 11. 声音打卡

**一句话**：用 60 秒读一段今天最喜欢的话，作为打卡的一部分。

- **为什么值得想**：声音比文字暖。另外，从 `exports/` 里的素材看，结营视频在尝试用声纹克隆来还原书友的声音；如果书友愿意，真实的朗读录音本身就是最好的结营素材。
- **新增**：录音、上传、存储、播放、音频内容安全检查。
- **必须先解决**：声音属于敏感个人信息。只在小程序内播放和用于结营视频、声音克隆是两种用途，后者必须单独、明确地征得同意，并且可以随时撤回和删除。
- **规模**：L，放最后。

### 其他小点子（顺手可做）

- **节气问候**：遇到节气，首页问候换一句（「今日立冬，宜早睡，宜读书」）。
- **同行榜**：排行榜改名「同行榜」，增加「全勤」分组，弱化一二三名。
- **掉队问候**：连续 3 天没读的书友，由管理员一键确认，以小凡的口吻发一条不催促的问候（「这几天没见到你，书还在这里」）。

## 七、建议节奏

功能要跟着期次走，不是跟着日历走：

| 时间点 | 上线内容 |
| --- | --- |
| 下一期开营前 | 方案一第一批（暖色底）；心情天气；慢递邮局的写信与封存；同行感 |
| 该期进行中 | 晨读日签；方案一第二批（首屏与仪式）；看见卡 |
| 该期结营前 | 慢递邮局的送达与拆信；我的 23 天；方案一第三批（手账） |
| 再下一期 | 摘抄本、小凡周信、实修清单；读伴和声音打卡视反馈决定 |

如果离下一期开营不到两周，建议只保「心情天气 + 慢递邮局写信」两项赶开营，其余顺延。

## 八、不建议做的

| 想法 | 为什么不做 |
| --- | --- |
| 积分、等级、勋章 | 字段已经在后端了（每次打卡 +10），但它会把读书变成刷任务，和这个营的气质相反。建议保持不展示 |
| 小程序里的实时 AI 对话（「问小凡」） | 小凡的价值是「认真读过你写的东西之后的回应」，不是秒回。另外面向用户的生成式 AI 服务在小程序平台有类目和资质要求，需要先确认；还有成本和内容风险 |
| 私信和群聊 | 微信群已经在做这件事；自己做要承担审核和骚扰治理 |
| 更强的竞争（PK、连胜榜） | 与「看见，不是评比」相反 |
| 全局深色模式 | 11-06 已决定不做，维持 |

## 九、所有新功能都要过的检查

1. **多租户**：新数据表带 `tenantId`，新板块能按租户开关（走现有的首页板块配置）。
2. **权限**：沿用现有的付费与社群权限判断，未报名和未激活的用户看到什么要逐项写清楚。
3. **内容安全**：我在代码里没有搜到微信内容安全接口（`msgSecCheck`、`mediaCheckAsync`）的调用，不确定是否在别处做了。凡是别人能看到的新内容（看见卡、书友信、声音）上线前要接；也建议评估现有的打卡和评论是否需要补。
4. **订阅消息**：每个新的推送场景都要在三个租户的公众平台各申请一个模板，并加进租户配置（现有 12 个场景键）。
5. **数据同步**：新数据表要加进 MongoDB 到 MySQL 的同步规则。
6. **包体**：新页面一律放分包（主包此前已超过 1.5MiB）。
7. **数据安全**：只做增量字段和新表，不跑任何初始化或重置脚本。
8. **测试**：小程序页面逻辑和后端接口都补 Jest 用例。
