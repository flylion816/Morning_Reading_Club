## Context

`backend/src/controllers/user.controller.js` 用 `Checkin.countDocuments` 统计累计打卡，得到的是打卡条数；`checkin.controller.js` 允许同一天多次打卡，连续天数字段 `User.currentStreak` 在每次打卡时累加，因此同一天重复打卡会被重复累加，断卡后也要等到下次打卡才归零。前端目前没有展示这些数字。小凡看见已有弹幕、朗读、长图分享，布局要保留。

## Goals / Non-Goals

- Goals:
  - 累计天数、连续天数、最长连续天数按自然日口径给出可信数字。
  - 「我的」成为手账：数字、日历、足迹一屏可见。
  - 小凡看见具备「信」的仪式感，且不破坏现有功能。
  - 课程详情与阅读体验补齐导航与个性化。
- Non-Goals:
  - 不迁移或改写历史打卡数据。
  - 不新增数据模型字段。
  - 不改租户主色、logo、Tab 图标图片；不做全局深色模式。
  - 不改小凡看见的生成、授权与分享逻辑。
  - 不为日历做统计分析或排行。

## Decisions

- Decision: 连续天数在读取时按自然日计算，而不是迁移存量数据。
  - 以用户时区（默认东八区）的自然日对打卡去重，再从今天（或昨天，视当天是否已打卡）向前数连续日。
  - 当天尚未打卡时，若昨天已打卡，则连续天数仍保留；昨天也没有则显示为 0，因此断卡后不必等下次打卡就会归零。
  - Alternatives considered: 写迁移脚本重算 `currentStreak`——涉及生产数据写入，风险高，且口径一变又要再迁一次。
- Decision: 累计天数 = 有打卡记录的不同自然日数量；最长连续 = 历史自然日序列中的最长连续段。
- Decision: 现有 `User.currentStreak` 字段保持不动，也不再作为展示依据，避免与旧逻辑冲突。
- Decision: 新增按月打卡日期只读接口，路由层挂载认证中间件，只返回当前登录用户该月有打卡的自然日列表；数据量小，不分页。
  - Alternatives considered: 前端复用现有打卡列表聚合——方案允许但依赖分页，月初月末会漏数据，接口更稳。
- Decision: 数字用数字字体令牌，日历今天用晨光色标出，打过卡的日子用主题色点亮。
- Decision: 共读足迹每期一枚印章（单字取自期次名），进行中的一期为空心章并附进度。
- Decision: 小凡的信复用现有数据与字段；「未读」以现有已读状态为准，若没有该状态则不显示火漆点而不是新增字段（见开放问题）。
- Decision: 「在场」使用第一批已建立的作用域深绿主题，本批只加邮戳、图标与衬线标题。
- Decision: 阅读设置面板的选择保存在本地存储，读取失败时回退默认（暖白、黑体、当前字号）。

## Risks / Trade-offs

- 口径校准会让部分用户看到数字变小 → 在发布说明里解释口径（按自然日去重），并用真实数据抽样对比新旧结果。
- 读取时计算增加查询开销 → 仅对当前用户的打卡日期做聚合，必要时对 `userId` 与打卡日期确认索引。
- 时区边界（零点前后打卡）→ 统一按东八区自然日，并补边界单元测试。
- 九步进度滚动联动在长页面上抖动 → 使用节流与固定锚点，并在真机验证。
- 夜间纸色与第一、二批的暖纸令牌冲突 → 夜间纸色仅限沉浸阅读页面作用域。

## Migration Plan

1. 后端先上线只读计算与只读接口，不改库；前端未更新时旧展示不受影响。
2. 再发布小程序，展示新数字、日历与足迹。
3. 回滚：前端回退版本即可，后端只读接口可保留。

## Open Questions

- 方案未写明「自然日」的时区；本变更假设按东八区。
- 方案未写明小凡看见是否已有「已读 / 未读」状态；若没有，火漆点与「给你留了一封信」需要另行评估后端字段，本变更暂不新增。
- 方案未写明最长连续天数的数据来源；本变更假设同样在读取时由打卡日期计算。
- 共读足迹印章单字的取法（取期次名首字还是后台配置）方案未给出。
