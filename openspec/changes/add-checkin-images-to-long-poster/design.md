## Context

课程详情页的打卡详情已经把 `detailCheckin.images` 规范化为图片 URL，并按正文、图片、标签的顺序渲染。长图生成由 `course-detail.js` 的 2D canvas 完成，当前只根据正文行数计算高度并绘制文字，因此图片没有进入海报布局。

长图生成还要处理微信 canvas 的尺寸、DPR 和导出失败。图片可能来自高分辨率手机原图，最多有 9 张，不能把所有原始图片对象长期保存在内存中。

## Goals / Non-Goals

- Goals:
  - 将打卡图片插入正文和标签之间，并保持详情页顺序。
  - 保留图片完整内容和原始宽高比。
  - 常规图片使用正文内容宽度；极端超长图片批次允许按比例整体缩小，但不裁剪、不拉伸。
  - 让图片加载失败、canvas 导出超时和高内存场景仍能生成可用长图。
- Non-Goals:
  - 不改变图片上传、存储、接口返回或详情页缩略图。
  - 不把富文本正文中的 `<img>` 另行解析为长图图片；本次只处理现有 `images` 字段。
  - 不新增第三方依赖或数据库迁移。

## Decisions

- Decision: 生成前按顺序获取每张图片的尺寸信息，生成布局元数据后再设置 canvas 尺寸。
  - 原因：图片高度必须参与总高度计算，否则正文、图片和标签会互相覆盖或被截断。
- Decision: 图片绘制宽度以正文内容区为基准（当前 canvas 为 1040，左右内容边距各 72），高度按 `sourceHeight / sourceWidth` 计算。
  - 原因：这样常规图片能与正文左、右边界对齐，同时保留原图比例。
- Decision: 图片最多使用一个受控的图片区高度预算；当多张极端长图超出预算时，统一降低图片显示比例。
  - 原因：不裁剪图片内容的前提下，避免 canvas 高度和像素内存随原图比例无限增长。常见横图、方图和少量竖图仍按正文宽度显示。
- Decision: 图片源按顺序处理；优先使用 `wx.getImageInfo` 和必要的 `wx.compressImage` 得到适合 canvas 的本地源，绘制时只保留当前图片对象。
  - 原因：把高分辨率源压到高于成图所需的有限宽度，可以减少解码内存；逐张绘制可以避免同时持有 9 张解码后的图片。
- Decision: 含图片或超过长图阈值的海报使用较低 DPR、JPEG 导出和现有的降尺度重试；图片准备失败只跳过该图片。
  - 原因：图片海报的主要内容是照片，适合用 JPEG；降级应保住正文、标签和二维码等结构。
- Decision: 现有完整生成失败时继续使用 fallback 海报；fallback 只截取正文，不裁剪已纳入布局的图片。
  - 原因：用户仍能获得完整图片和可读的分享图，同时保留原有超长正文降级行为。

## Risks / Trade-offs

- 超长竖图在极端情况下会比详情页缩略图高很多；统一比例缩小会让它窄于正文区，但能保留全部图片内容并控制 canvas 内存。
- `wx.getImageInfo` 或 `wx.compressImage` 在部分基础库不可用时会回退到原 URL；若 URL 无法在 canvas 中加载，该图片会被跳过，长图其余内容仍可生成。
- 含图片海报使用 1x 逻辑导出和 JPEG，照片细节优先于无图片海报的高 DPR PNG。
